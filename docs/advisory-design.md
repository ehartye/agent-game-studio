# Advisory Studio design

Studio supplies eight optional game-development roles. Each skill explains when it helps, the advice and process guidance it offers, and the wiki documents or backlog items it maintains when engaged. Technical and craft implementation guidance remains with specialist plugins referenced by the plugin map.

The roles do not intercept every game request, prescribe a response preamble, enforce readiness or fit gates, require a second approval after an instruction to proceed, restrict authorized file changes, forbid test reruns, demand blind reviews, or write records after every consultation. Project conventions and genuine host permissions remain in force. Evidence and approval records must describe observed facts and actual decisions.

Maintained Studio state has one canonical home in the project's wiki. No local state fallback, sidecar tracker or duplicate progress file is created. Existing project-owned records can be consulted and linked; they are not automatically relocated, deleted or converted. Ordinary code, assets, test output and static instruction pointers are outside this state boundary. If the wiki is unavailable, advice and authorized implementation continue; a requested wiki update can be reported as pending.

An instruction-file block is absent by default. A project can use a short static pointer to its actual records and Studio's optional advisory role. Studio supplies no host instruction precedence policy and performs no automatic consumer migration.

The shared references retain useful planning questions, role selection, artifact examples and optional review guidance. Templates offer useful fields rather than closed schemas or mandatory document sets. Historical specs and trial reports remain labeled as history so old observations are not presented as evidence for this design.

## Validation

Repository checks validate structure, links, public-safe content and selected regressions. Scenario definitions cover direct small changes, absent documents, authorized edits, explicit delegation, iterative debugging, wiki-only Studio state and truthful reporting. Static checks cannot establish how a live host follows prose; host trials require separate transcripts and workspace evidence.

## Existing projects

The earlier adoption guidance treated existing documents outside the wiki as adopted catalog artifacts in place. That could leave a Studio-maintained record outside the wiki even though newly created records used wiki paths. The revised adoption and catalog guidance distinguish existing project-owned context from Studio-maintained state and keep the latter in the wiki.

No consumer files are changed by this refactor. A project using an external document as a Studio record may need an explicitly scoped transition to a canonical wiki record; preserve its history and references, and avoid maintaining two competing copies. There is no automatic relocation, deletion or instruction-file migration.
