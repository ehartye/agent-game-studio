# studio-start

## When it helps

Use when asked for project orientation, help finding records or roles, or a lightweight introduction to Studio.

## Advice and process

Start with the user's task and the context already available. Locate only the records that help: a brief, architecture, backlog, roadmap, design notes or evidence. An existing status page can be useful, but its absence or age does not trigger adoption or prevent work.

Offer a relevant role from [decision routing](../../references/decision-routing.md) when another perspective would help. Roles can be used directly; this skill is not an interceptor for every game request and does not require a routing preamble or fixed status report.

For a new project, help identify a useful first step and offer a brief or small plan if wanted. For an existing project, [adoption guidance](../../references/adoption.md) means using its current records and conventions. Do not bootstrap a required document set or migrate owner documents to satisfy Studio templates.

## Documents and backlog

Maintain an optional artifact map or [state page](../../references/templates/state-page.md) in the project wiki when asked or useful for coordination. Point to actual existing paths, summarize known work and distinguish unknowns from blockers. The [artifact catalog](../../references/artifact-catalog.md) is a menu of useful records, not a checklist to complete.

No instruction-file block is added by default. If a pointer would help, use the tiny optional [instruction block](../../references/templates/instruction-block.md) with actual project paths, following [instruction-file guidance](../../references/instruction-files.md). Do not choose an authoritative instruction file or reorganize the project's instructions on Studio's behalf.

A quick orientation can be an answer alone. Missing wiki tooling or a state page is not a blocker; use the project's available records and tools. See the [plugin map](../../references/plugin-map.md) for optional document and specialist tooling.

## Working with the project

Use existing project conventions, user instructions and host permissions. Studio adds no approval gates or controls over file editing, testing, release or workflow. Missing documents do not prevent useful work. Act within explicit delegation; an authorized request to proceed does not need a second Studio approval. Record decisions as delegated when that is their basis, and never invent owner approval or observed results.

A consultation can end with advice alone. Maintain Studio records only in the project's wiki, their single canonical home; do not create repo-local Studio state, sidecar trackers or duplicate progress records. Existing project-owned documents remain useful context and are not automatically Studio records. Do not relocate or delete them to satisfy a template. Missing wiki access does not block advice or authorized source work; report any requested wiki update that could not be completed. See [shared guidance](../../references/process.md).
