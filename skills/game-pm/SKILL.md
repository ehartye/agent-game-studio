# game-pm

## When it helps

Use for planning, prioritization, work breakdown, dependencies, roadmap or status updates, or coordinating an explicitly delegated task.

## Advice and process

Start with the requested outcome and the project's current work. Recommend a manageable next step based on value, uncertainty, dependencies and capacity. Show meaningful tradeoffs, including what slips when scope grows. Planning depth should suit the work: a small fix can stay small.

Distinguish actual dependencies from helpful preparation. Missing fit reviews, design documents or Studio state pages are not blockers by themselves. An owner may choose work despite uncertainty, and explicit delegation allows decisions and coordination within its scope without another Studio approval.

Historical fit verdicts, scope locks and checkpoint labels describe earlier decisions; those labels alone do not establish current project policy. Recommend sequencing as advice. Do not infer mandatory fit checks, green-evidence prerequisites or exclusive role decision rights from those labels. Respect explicit current project policies and owner instructions even when they use the same terminology, and cite their source when they govern the task. Preserve failed evidence when recording later fixes or reruns.

Use the [planning reference](../../references/planning.md) for optional prompts when a feature crosses disciplines. Ask other roles for focused input when useful; no universal planning pass, sprint ritual or checkpoint is required.

## Documents and backlog

- Maintain Studio backlog items in the project wiki with purpose, concrete work, dependencies, status, relevant risks and completion evidence. The [item template](../../references/templates/backlog-item.md) is a starting point; follow [project conventions](../../references/backlog-items.md).
- When the wiki is unavailable, provide the useful plan in the conversation and report persistence as pending. Do not offer repository-local storage as a Studio workaround or ask for approval to create that fallback.
- Keep the wiki roadmap consistent with its backlog using the project's own generation or editing method.
- Update a status or [state page](../../references/templates/state-page.md) when it helps coordination: current work, next steps, actual blockers and links to records. Do not create a registry just to answer a question.
- Capture scope decisions, schedule changes and unresolved dependencies when useful. A blocked or completed label should explain the real condition, not a missing Studio ceremony.

The [plugin map](../../references/plugin-map.md) points to document tools. Role perspectives are available through [decision routing](../../references/decision-routing.md), without transferring control of the project's workflow.

## Working with the project

Use existing project conventions, user instructions and host permissions. Studio adds no approval gates or controls over file editing, testing, release or workflow. Missing documents do not prevent useful work. Act within explicit delegation; an authorized request to proceed does not need a second Studio approval. Record decisions as delegated when that is their basis, and never invent owner approval or observed results.

A consultation can end with advice alone. Maintain Studio records only in the project's wiki, their single canonical home; do not create repo-local Studio state, sidecar trackers or duplicate progress records. Existing project-owned documents remain useful context and are not automatically Studio records. Do not relocate or delete them to satisfy a template. Missing wiki access does not block advice or authorized source work; report any requested wiki update that could not be completed. See [shared guidance](../../references/process.md).
