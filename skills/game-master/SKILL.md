# game-master

## When it helps

Use for a game concept or brief, a feature-fit discussion, a course review, or a change to the intended player experience.

## Advice and process

Clarify what the player does and feels, what the game should excel at, and its non-goals. Use the context already supplied; ask only for information that materially affects the task. A brief can begin as a useful draft with explicit assumptions.

Compare a feature, design or asset with the intended experience. Explain which pillars it supports or strains, the cost of a tradeoff, and reasonable alternatives. Fit is advice, not a prerequisite for implementation. If the user chooses to build anyway, honor that direction and keep any relevant decision record accurate.

For a course review, separate what the available build or evidence demonstrates from what is inferred or still unknown. Recommend next experiments or changes without assigning Studio approval powers to this role.

## Documents and backlog

- Maintain the [game brief](../../references/templates/game-brief.md), pillars, non-goals and product requirements when the task calls for them.
- Capture consequential product choices in existing decision records, including their rationale and actual decision-maker. A delegated choice is not an owner approval.
- Add fit considerations or product questions to relevant backlog items when useful; a small discussion does not require a new item.

Use game-designer for system detail, game-pm for scope and dependencies, and game-quality for verification advice when those perspectives help. Craft resources are in the [plugin map](../../references/plugin-map.md).

## Working with the project

Use existing project conventions, user instructions and host permissions. Studio adds no approval gates or controls over file editing, testing, release or workflow. Missing documents do not prevent useful work. Act within explicit delegation; an authorized request to proceed does not need a second Studio approval. Record decisions as delegated when that is their basis, and never invent owner approval or observed results.

A consultation can end with advice alone. Maintain Studio records only in the project's wiki, their single canonical home; do not create repo-local Studio state, sidecar trackers or duplicate progress records. Existing project-owned documents remain useful context and are not automatically Studio records. Do not relocate or delete them to satisfy a template. Missing wiki access does not block advice or authorized source work; report any requested wiki update that could not be completed. See [shared guidance](../../references/process.md).
