# Using Studio in an existing project

There is no required adoption ceremony. Use a relevant role on the current task. Existing code, documents, trackers and agent instructions retain their meaning.

When asked to orient or organize records:

1. Inspect relevant existing records and code, avoiding secret values.
2. Map useful documents to actual locations; a document may serve several purposes.
3. Identify gaps that matter to the task. Distinguish unknown intent from facts recoverable from code or history.
4. Maintain Studio records in the project's wiki, their single canonical home. Link existing project-owned documents without automatically reclassifying, relocating or deleting them.
5. Summarize uncertainties and useful next work. A backlog or state page is optional.

Authorized existing-file edits and explicit delegation follow normal project and host rules. Studio adds no special approval for an overwrite, rename, deletion or role-owned document edit. Preserve unrelated content; do not replace owner documents just to match templates.

No instruction block is added by default. If useful and within the task, use the tiny optional [pointer](templates/instruction-block.md) with actual existing wiki paths. Do not automatically modify other projects. There is no required tooling audit, phase placement, rigor tier or bootstrap record.

For a project with a long history, draft a requested brief in one pass from its records, separating known intent from proposals. Label reconstructed material and sources. Missing approval dates remain missing; delegated choices are recorded as delegated.

If wiki access is missing, continue advice or authorized source work and report any pending wiki maintenance. Do not create repository-local state or sidecar trackers.
