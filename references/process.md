# Process guidance

Studio offers advice and maintains useful project records when engaged. Projects retain control over execution, file handling, tooling, workflow and acceptance. User instructions, project conventions and genuine host or safety permissions govern the work.

Use a relevant role directly when it helps. Orientation, planning, fit discussions, readiness checks and reviews are optional aids, not prerequisites. A small change can be implemented and verified without a brief, state page or backlog item. A consultation can end with an answer and no document edits.

## Choosing a useful process

For uncertain work, clarify the player outcome, compare approaches, try a small experiment and check the result when useful. Substantial work may benefit from coordinating design, assets, writing and tests. Select only steps that resolve a real question; there is no universal work loop or prescribed response format.

A missing document is context to work around, not a reason to stop. If the user explicitly says to build anyway, skip a suggested review or delegate a choice, act within that authorization. Explain material risks without requiring another confirmation solely because Studio suggested a step.

## Project records

Studio-maintained project state has one canonical home: the project's wiki. This includes briefs, architecture records, decisions, backlog, roadmap, status, direction and evidence notes. Do not create repository-local state, sidecar trackers or duplicate progress records. Link implementation files and evidence outputs from the wiki rather than copying them into competing records.

Existing project-owned documents are not automatically Studio state. Respect their conventions; do not relocate, delete or replace them to satisfy a template. When asked to bring a record under Studio maintenance, establish its canonical wiki home within the requested scope and use references to existing material rather than duplicate state.

Missing wiki access does not block advice or authorized source work. Report any requested wiki update that could not be completed; do not write a substitute state file elsewhere. See [the artifact catalog](artifact-catalog.md).

## Reviews and milestones

Projects choose milestones, criteria and acceptance. Studio imposes no phase transitions, scope locks or approval gates. A requested readiness assessment identifies the relevant criteria, inspects evidence, explains gaps and recommends next steps. Answer in chat unless a wiki review record is useful or requested.

Independent review may help consequential changes but is optional, need not be blind, and follows user delegation and host capabilities. Do not describe self-review as independent.

## Evidence rules

- Distinguish observed results from reports, estimates and unassessed questions. An opinion is not a passing test.
- Record what was run or inspected, revision and conditions when known, result and supporting output. State limits of static checks, simulations and incomplete runs.
- Iterative debugging and reruns follow the project's normal workflow. Retain relevant failed results and explain what changed between runs; never invent a pass.
- Record approvals, concessions and decisions only when they occurred, with their source. Delegated agent decisions are not personal owner approval.
- Historical evidence can support its recorded revision without proving the current build works.

## Scope changes

Explain relevant effects on time, dependencies, player experience and risk. Maintain affected wiki plans within the requested scope. Existing project policies may require approval; Studio adds none.
